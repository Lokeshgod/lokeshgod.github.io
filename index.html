CASE STUDY / 01 APPROVED SUBMISSION

PROJECT FENRIR · C++ / LIBFUZZER

From a crafted input to a root-cause repair.

A structured binary-input path reached an unbounded allocation in a windowed decoder. The evaluation asked more than “can an agent stop the crash?”—it required tracing the failure through actual project code, producing a reproducible proof, and preserving intended behavior after repair.

C++libFuzzerCrash reproductionRoot-cause patching
HISTORICAL EVIDENCE Approved

Recorded approval of a C++ fuzzing task; historical model-calibration results indicated a difficult but solvable failure.

Key lesson

A grader must reject symptom suppression and accept genuine repairs that maintain regression behavior.

CASE STUDY / 02 ACCEPTED TASK SET

PROJECT STARFISH · ENGINEERING COMPUTATION

Verifying a solution from first principles.

Engineering coding tasks connected raw observations and physical constraints to an auditable design decision. In a grounding-system case, the verifier independently reconstructed circuit and exposure calculations across a multi-scenario robustness audit instead of trusting a hardcoded expected-output file.

CASE STUDY / 03 LOCAL VALIDATION

PROJECT ODYSSEY · STATEFUL SYSTEMS

Correctness across time, state, and failure.

A long-horizon event-processing task combined revisions, retractions, exactly-once sequencing, watermarks, snapshots, crash recovery, and an indexed workload. A candidate needed to preserve interacting invariants across operations and restarts—not just make isolated unit tests pass.

PythonEvent processingRecoveryConcurrency
LOCAL VERIFICATION 49 / 49

Reference passed 49 local sealed checks in 12 groups. Earlier hosted version did not satisfy the long-horizon difficulty gate; revised hosted acceptance is unconfirmed.

Key lesson

Good long-horizon benchmarks make independently reasonable fixes interact—and verify the combined behavior.

03 / HOW I WORK

A benchmark is only
as good as its grader.

The difference between testing a model and testing its ability to guess what a benchmark author wanted.

01 / CONTRACTS

Specify observable behavior.

Frame a realistic engineering task around inputs, outputs, invariants, edge cases, and the limits of acceptable solutions.

02 / REFERENCE

Prove it can be solved.

Build a reference path and preserve a broken baseline. Record exactly what changed and which checks must flip.

03 / GRADING

Verify properties, not strings.

Recompute from source inputs where possible; enforce identity coverage, deterministic ordering, regression safety, and anti-shortcut checks.

04 / CALIBRATION

Inspect partial failures.

Compare local baseline and reference runs, analyze which invariants fail, and label hosted or live-agent results only when they exist.
